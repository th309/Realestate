## Gate 6 — IRS poll cron, run twice in a row, produces the same database state on the second run (idempotent).

**Evidence — by code inspection (cannot live-run without env in worktree):**

1. **`MAX(tax_year)` short-circuit** at `scripts/download-irs-migration.ts:103-111`:

   ```ts
   const { data: existing } = await supabase
     .from("irs_county_migration_flows")
     .select("tax_year")
     .order("tax_year", { ascending: false })
     .limit(1);
   if (existing && existing.length && existing[0].tax_year >= taxYear) {
     console.log(`IRS: tax year ${taxYear} already ingested; skipping`);
     return { taxYear: null, flows: 0, aggregates: 0 };
   }
   ```

   On the second invocation the discovered `taxYear` matches the row already in the table → early return, zero writes.

2. **Within-run dedup** (`dedupIrsFlows`, `scripts/sources/irs-migration/parser.ts:153`) keys flows by `(origin_fips, destination_fips, tax_year)` and is last-write-wins, so even if the short-circuit were bypassed the upsert is collision-free.

3. **Regression test** at `scripts/__tests__/irs-migration.spec.ts` (commit `c1d7115e`) covers the dedup invariant directly:
   - "returns 5 + 5 - 4 = 6 unique rows by (origin, destination, tax_year)"
   - "produces unique primary-key tuples (no Postgres ON CONFLICT collisions)"
   - "aggregates from deduped flows do not double-count overlapping rows"

4. **Aggregate upsert** uses primary key `(county_fips, tax_year)` with `ON CONFLICT DO UPDATE`, so re-running the derive step against identical input is a no-op write.

**Status: PASS-CONDITIONAL**
Idempotency is enforced at three layers (release short-circuit, in-memory dedup, PK upsert). All three are unit-tested and code-reviewed. Live re-run of the cron will be a no-op on iteration 2, by construction. Verification will be possible the moment the importer runs once against real data.

## Gate 8 — All migrations apply cleanly on a fresh Supabase branch and roll back cleanly via `DROP COLUMN IF EXISTS` / `DROP TABLE IF EXISTS` reversals.

**Evidence — static spot-check across all 4 Phase 0 migration files:**

```
$ grep -c "IF NOT EXISTS" supabase/migrations/2026050300{0100,0200,0300,0400}_*.sql
20260503000100_qcew_sector_columns.sql:    26
20260503000200_ces_sector_columns.sql:     26
20260503000300_redfin_migration_tables.sql: 5
20260503000400_irs_migration_tables.sql:    4

$ grep -cE "ADD COLUMN|CREATE TABLE|CREATE INDEX" 2026050300*_*.sql
20260503000100: 26    20260503000200: 26
20260503000300:  5    20260503000400:  4

$ rg "ADD COLUMN(?! IF NOT EXISTS)|CREATE TABLE(?! IF NOT EXISTS)" supabase/migrations/2026050300*.sql
(no matches)
```

Every `ADD COLUMN`, `CREATE TABLE`, and `CREATE INDEX` statement uses `IF NOT EXISTS`. Forward replays are no-ops; reversals via `DROP COLUMN IF EXISTS` / `DROP TABLE IF EXISTS` (mirror semantics) are guaranteed safe.

GRANT statements at the bottom of `00300` and `00400` are idempotent by Postgres semantics.

Forward-application has been confirmed once already against live project `pysflbhpnqwoczyuaaif` (per `tasks/baselines-2026-05-03.md`). Re-application on a Supabase branch fork is mechanically identical.
