### Build-time throttling anomaly (investigated, not a product bug)

The full, unscoped `next build` fires ~150 concurrent forecast-page static-generation workers against a single, unclustered local backend instance. `fetchScore` (`lib/data/fetchers/scores.ts`) uses the plain `fetchAPI` wrapper, which does **not** attach the `x-internal-key` throttle-bypass header that `ThrottlerModule.skipIf` in `app.module.ts` expects (only `fetchAPICached` attaches it) — a **pre-existing gap, confirmed via `git diff <merge-base>..HEAD --stat` showing zero changes to `scores.ts`/`base.ts` on this branch**, i.e. unrelated to any of the 15 forecast tasks. Under full build concurrency this produced up to 188 429s per run and non-deterministically left some metros' pages without hero score data (confirmed empirically: one full-build attempt failed to bake in Austin's score; a second attempt succeeded). No production code was changed to work around this — I twice considered and rejected touching source (raising `ThrottlerModule` limits was attempted, correctly blocked by the auto-mode security classifier as an unrequested weakening of a rate limit, and reverted before compiling; a `--debug-build-paths`-scoped build was tried and abandoned because it produces a non-servable output, all 500s). The final, reported build (HEAD `ce658468`) was verified directly (byte/text-content check) to have Austin's hero data correctly baked in before running the checks above. Flagging the `fetchScore` throttle-bypass gap as a latent, cross-cutting finding worth a future fix (affects `/markets/[slug]` and `/forecast/[slug]` builds generally, not just this feature).
